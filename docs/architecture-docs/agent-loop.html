Agent Loop

Autonomous agent execution: planning, strategy, and tool use

Overview

The agent loop is the autonomous execution engine of the AIBot Framework. It runs independently of Telegram messages, allowing bots to pursue goals, execute plans, and take actions proactively.

The loop was refactored from a single monolithic agent-loop.ts (1,482 lines) into a family of focused modules. The main orchestrator agent-loop.ts (724 lines) delegates to: agent-scheduler.ts (scheduling and concurrency), agent-retry-engine.ts (retry logic), agent-planner.ts (plan generation), agent-strategist.ts (strategic oversight), agent-loop-utils.ts (shared utilities), and llm-json-parser.ts (generic JSON parsing). Supporting modules include agent-loop-prompts.ts (prompt templates), agent-feedback-store.ts (human feedback persistence), ask-human-store.ts (human-in-the-loop questions), ask-permission-store.ts (human-in-the-loop permission requests), and tool-executor.ts (centralized tool execution engine).

Phase Diagram

Each agent loop cycle follows this sequence of phases. The strategist runs conditionally every N cycles.

Operating Modes

The agent loop supports two distinct operating modes, configurable per bot via botConfig.agentLoop.mode.

Periodic Mode Default

Runs at configurable intervals (e.g., every 5 minutes). The bot sleeps between runs using an interruptible sleep mechanism that can be woken via wakeUp().

Key Config

everyInterval duration string (e.g. "5m", "1h"). Parsed by parseDurationMs().
maxDurationMsHard timeout per cycle. A session timeout guard triggers at 80% of this limit.

Behavior

Each bot gets its own async loop via runBotLoop(). After execution, sleep duration is computed from config. On transient errors (timeout, network), exponential-backoff retries are attempted before falling back to the normal 5-min+ sleep cycle.

Continuous Mode Advanced

Runs back-to-back cycles with only a short configurable pause between them. The bot stays active as long as it has work to do.

Key Config

modeSet to "continuous" on the per-bot agentLoop config.
continuousPauseMsMilliseconds to wait between back-to-back cycles (default: 5000).
continuousMemoryEveryLog to memory every N cycles to avoid flooding (default: 5).

Tracking

Tracks continuousCycleCount and sessionStartAt per bot schedule. Uses a separate continuous planner prompt that includes the last cycle summary for context continuity.

Strategist

The strategist is the strategic oversight layer, implemented in agent-strategist.ts. It runs conditionally every N cycles (configured via strategist.everyCycles) and only when the minimum interval has elapsed (strategist.minInterval). Both conditions must be met (AND logic).

What It Does

Reviews goals and recent activity (last 7 days), performs goal operations, sets focus for upcoming cycles, and provides strategic reflection.

Goal Operations

The strategist can perform four types of goal operations. Added goals are automatically tagged with source: strategist:YYYY-MM-DD for provenance tracking. The reflection skill can also append goals with source: reflection:YYYY-MM-DD.

Action Description Fields
add Add a new goal to active list goal, priority?, notes?
complete Move goal from active to completed goal (substring match), outcome?
update Modify an existing active goal goal (substring match), status?, priority?, notes?
remove Delete a goal from active list goal (substring match)

Output Format: StrategistResult

interface StrategistResult {
  goal_operations: GoalOperation[];
  focus: string;           // 1-2 sentence directive for next cycles
  reflection: string;      // Analysis of agent's current state
  next_strategy_in?: string; // Suggested next run, e.g. "6h"
}

Behavioral Pattern Analysis

The strategist prompt includes a Behavioral Pattern Analysis section that instructs the LLM to classify recent actions into types (CONTENT, OUTREACH, RESEARCH, ASSESSMENT, MAINTENANCE) and detect behavioral ruts (>70% same type) and engagement gaps (outputs without feedback).

When the agent loop computes behavioral metrics from recent actions, a Current Behavioral State section is injected with concrete data: Shannon entropy, dominant action type %, and engagement ratio. This gives the strategist evidence-based signals to force mode shifts (e.g., switch from content creation to assessment or outreach).

Engagement Gate

Configurable per-bot via agentLoop.engagementGate. Detects when a bot produces outputs without confirmed feedback. Two modes:

  • soft (default): Warning injected into planner prompt
  • hard: Blocks content creation in planner until feedback is received
engagementGate: {
  enabled: true,    // default
  mode: 'soft',     // 'soft' | 'hard'
  threshold: 5      // outputs without feedback before trigger
}

Retry Behavior

The strategist uses runStrategist() with up to 1 retry. First attempt uses temperature 0.4, retry uses temperature 0. JSON parsing is handled by the shared parseLLMJson<T> utility from llm-json-parser.ts. If both attempts fail to produce parseable JSON, the strategist result is null and the cycle continues without strategic guidance.

Planner

Planner logic lives in agent-planner.ts. Each cycle, the planner makes a lightweight LLM call to decide whether to act and what steps to take. It receives the full bot context: identity, soul, motivations, goals, available tools, recent memory, feedback, and the strategist's focus. A unified runPlannerWithRetry() handles both periodic and continuous modes.

Priority Levels

PriorityMeaning

mediumRoutine work, exploration, incremental progress
lowCreative exploration, boundary-pushing, novel research
noneNothing novel to do. Empty plan required. Triggers idle tracking.

Novelty Imperative

The planner prompt includes a strong Novelty Imperative: repeating the same action is treated as worse than doing nothing. A recentActionsDigest is built from the bot's last 24 hours of actions, flagging patterns repeated 2+ or 3+ times. Anti-patterns such as "reviewing goals just to review them" or "saving reflections to memory" are explicitly banned.

Retry Behavior

Uses runPlannerWithRetry() (from agent-planner.ts) with 1 retry. First attempt at temperature 0.3, retry at 0. JSON parsing uses the shared parseLLMJson<T> from llm-json-parser.ts. If parsing still fails, returns an idle plan (priority: 'none') rather than generating busywork.

Planner Backend

The planner and the strategist are generate() calls; the executor is a tool-calling chat(). Until August 2026 all three went through the bot's wrapped client, and LLMClientWithFallback.generate() re-issues any non-permanent Claude CLI failure to the Ollama fallback silently — so the planner and strategist of every claude-cli bot ended up running on glm-5.2:cloud, exhausted the shared Ollama Cloud weekly quota, and the llm-query-log kept saying backend: 'claude-cli'.

The wider fix: cross-backend fallback is opt-in

2026-08-22 Pinning the planner only fixed the planner. The root cause was createLLMClient() itself: with no failover chain configured it returned LLMClientWithFallback(claude, ollama) for every llmBackend: 'claude-cli' caller — the reflection skill, the soul health check, the quality reviewer, the memory consolidator and the whole conversation path, not just the agent loop. A claude-cli bot now gets the bare ClaudeCliLLMClient unless claudeCli.crossBackendFallback (default false) is turned on. With failover.enabled, orderCandidatesByBackend() puts the bot's own backend first in the chain and resolveOllamaModels() supplies the real configured Ollama models — the primary used to be ollamaClient.toString(), the literal string [object Object].

Executor

The executor takes the planner's steps and carries them out using the full LLM tool-calling interface. It builds a system prompt via SystemPromptBuilder in autonomous mode and sends the plan as a user message via buildExecutorPrompt().

File Tree Scanning

Before building the executor prompt, scanFileTree() (from agent-loop-utils.ts) walks the bot's workDir (max depth 3, max 100 entries) and passes the result as fileTree to buildExecutorPrompt(). When the directory is empty or missing, the prompt explicitly tells the LLM that the directory is empty and to use file_write only — preventing blind file_read/file_edit attempts on non-existent files.

When productions.enabled === false for a bot, the file tree scan is skipped entirely and the executor prompt omits the "Working Directory Contents", "Production Directory Rules", and file-centric tool usage instructions. This saves context tokens and prevents the LLM from being pushed toward file production for bots that should focus on conversations, research, or goal management. The productionsEnabled flag is passed via ExecutorPromptInput.

Karma on the Executor Path

Tool errors are debited per failing call by ToolExecutor through KarmaService.recordOutcome(botId, 'toolError', …) (execution and validation phases, rewards.toolError = -1 by default, deduped per tool + message by the automated-negative cooldown). A non-repeated cycle is worth rewards.novelAction (0 by default — activity is not impact); a repeated plan still costs -2. See Karma Outcomes & Trait Policy.

Execution Flow

The AgentLoop creates a ToolExecutor instance per cycle, then calls executor.createCallback() to get a function compatible with LLMClient.chat(). The LLM makes tool calls, which the callback dispatches through the executor. After the LLM conversation finishes, executor.getExecutionLog() retrieves all recorded tool calls for the cycle result.

ToolLoopDetector

src/bot/tool-loop-detector.ts
Detects when an LLM is stuck in repetitive tool call patterns and provides warning/blocking signals to break the loop. Adapted from OpenClaw's tool-loop-detection.ts with architectural changes to fit the ToolExecutor class pattern.

4 Detection Strategies

DetectorPatternLevels
global_circuit_breaker Same tool+args+result repeated past absolute ceiling Critical only (default: 25)
known_poll_no_progress Configurable "poll" tools returning identical results Warning (8) / Critical (16)
ping_pong A↔B alternating call patterns with no progress Warning (8) / Critical (16, requires no-progress evidence)
generic_repeat Same tool+args repeated (result-aware: skips if results differ) Warning only (8)

Integration Flow

The AgentLoop creates a ToolLoopDetector from the agentLoop.loopDetection config (merged global + per-bot overrides) and passes it to ToolExecutor via options. Inside execute():

  1. Pre-check: detector.check(name, args) before execution. Critical → block and return error. Warning → capture message.
  2. Record: detector.recordCall(name, args) after tool runs.
  3. Outcome: detector.recordOutcome(name, args, result) with content hash.
  4. Inject: If warning was captured, append [LOOP WARNING: ...] to result so the LLM sees it in context.

Configuration

  "enabled": true,            // default: true
  "historySize": 30,          // sliding window
  "warningThreshold": 8,
  "criticalThreshold": 16,
  "globalCircuitBreakerThreshold": 25,

    "genericRepeat": true,

User Awareness

The agent loop can be configured to scan session metadata and inject a summary of recently active users into the planner prompt. This enables coach bots and other proactive agents to see who is active and send messages to them.

Configuration

config.json → agentLoop.userAwareness
{
  "enabled": false,            // default: false
  "activeWindowHours": 24,     // look back window (1-168)
  "maxUsers": 5                // max users in summary (1-20)
}

Per-bot overrides via bots[].agentLoop.userAwareness (same fields, all optional).

How It Works

  1. buildActiveUsersSummary() scans SessionManager.listSessions() for keys matching bot:{botId}:private:*.
  2. Filters by lastActivityAt within the configured time window.
  3. Sorts by most recent, takes top N users.
  4. Returns a markdown table injected into the planner system prompt.

Feedback System

The AgentFeedbackStore allows humans to submit feedback to bots via the web dashboard. Feedback is processed at the beginning of each agent loop cycle, before the strategist and planner run.

AgentFeedbackStore

Lifecycle

StepDescription

2. DetectAt cycle start, getPending(botId) checks for unprocessed feedback.

Engagement Gate

Production without feedback is waste. The gate compares outputs produced against human feedback received and, in hard mode (the default since 2026-08-21), refuses to let the bot produce more content until somebody reacts.

2026-08-22 The hard gate shipped on 2026-08-21 was inert in production. detectUnconsumedOutput() counted the in-memory recentActions window, which is rebuilt from scratch on every restart — so bots sitting at 51–65 unconsumed outputs never reached the threshold. The output count now comes from durable state.

Configuration (BotAgentLoopOverrideSchema.engagementGate)

Per-bot only — bots[].agentLoop.engagementGate. There is no agentLoop.engagementGate on GlobalAgentLoopConfigSchema; when the block is absent the runtime defaults below apply. 

engagementGate: {
  enabled: true,        // default true
  mode: 'hard',         // 'hard' (default) downgrades CONTENT plans to idle; 'soft' only annotates the prompt
  threshold: 5,         // outputs with zero feedback before the gate triggers (1–50)
  lookbackHours: 168    // how far back durable output and feedback are counted (1–720; 7 days, matching
                        // BotSchedule.feedbackEvents retention)
}

Where the output count comes from

Neither wiredAgentLoop.countDurableOutputs() returns null and the gate falls back to the in-memory recentActions window

resolveDurableOutputCount() picks the ledger when it has anything, the changelog otherwise. The human_inbound event

2026-08-22 ConversationPipeline.handleChannelMessage() emits human_inbound (HUMAN_INBOUND_HOOK, declared in agent-loop-utils.ts) with { botId, channelKind, chatId, userId?, timestamp }. AgentScheduler subscribes on start() and unsubscribes on stop(), turning each event into a human_message feedback event and a humanReply karma credit. The exported predicate isHumanInboundMessage(msg, { isPeerAgent }) filters out peer agents (resolved through AgentRegistry), channelKind: 'mcp', synthetic: true, cron--prefixed message ids and blank text.

The event travels on the raw EventEmitter, deliberately outside the typed HookEvents map — src/bot/hooks.ts still declares exactly eight lifecycle events. Telegram never calls handleChannelMessage(), so it cannot double-count; but it does not count at all either: AgentScheduler.requestImmediateRun() is only reachable through BotManager.requestImmediateAgentRun(), which has no callers outside tests.

Answers, feedback and messages are kept as BotSchedule.feedbackEvents (AgentScheduler.recordFeedbackEvent(), 7-day retention, persisted with the schedule) because the stores they come from are consumed destructively. Every source is best-effort: a failing service contributes zero rather than breaking the cycle. The total is passed to detectUnconsumedOutput(recentActions, threshold, externalFeedbackCount), so a bot that is actually being answered is not gated, and to buildRecentActionsDigest() for the prompt.

Removed 2026-08-22 detectUnconsumedOutput() used to scan the bot's own plan summaries for received|confirmed|responded|feedback|approved|denied|answer and count a match as feedback — a bot could un-gate itself simply by writing the word "feedback" in a summary. A self-run ASSESSMENT plan also used to count. Both are gone: feedback is now exactly the externally-sourced count.

Enforcement (evaluateEngagementGate())

When the gate is triggered (outputCount ≥ threshold and feedbackCount === 0) the planner prompt carries a HARD ENGAGEMENT GATE note. If the planner still returns a plan classified as CONTENT, the cycle is downgraded to idle with the summary Engagement gate: content blocked until feedback (N outputs, 0 feedback), an agent:idle activity event and a warn log listing the feedback signals. OUTREACH, ASSESSMENT, RESEARCH and MAINTENANCE plans pass — they are how the bot earns feedback. Soft mode never blocks.

The trigger log line (info, "Agent loop: engagement gate triggered") carries outputCount, outputSource, feedbackCount, lastFeedbackAt and mode, so an operator can tell a genuine gate from a cold-start artefact. The hard-block warn adds the full feedbackSignals breakdown and the first three plan steps.

Flow

StepDescription
1. AskAgent calls ask_human tool. AskHumanStore.ask() registers the question and returns a promise.
2. DisplayQuestion appears in the web dashboard inbox and optionally as a Telegram message.
3. AnswerHuman answers via web (answerById()) or Telegram reply (handleReply()). Promise resolves.
4. ConsumeNext agent loop cycle calls consumeAnswersForBot() before the strategist runs, so the answers count as engagement feedback for that cycle. Answered questions are injected into the planner context as top priority.

6. Auto-closesweepStaleAskHumanQuestions() (run on every ask_human call for the calling bot) calls AskHumanStore.closeStale() on asks older than askHuman.autoCloseHours (72 h): the promise rejects with an auto-close reason, the inbox conversation is marked closed, and a [ask_human] Question auto-closed after 72h without answer: … line is appended to the bot's daily memory so it knows the question went unanswered.

Reply Matching

When a Telegram reply arrives, handleReply() first tries to match by replyToMessageId. If no reply-to but exactly one pending question exists in that chat, it matches automatically. Answered questions are stored in a separate map and consumed by the agent loop on the next cycle.

Dismissal

Questions can be dismissed via dismissById(), which rejects the promise with an error. The agent sees this as a timeout and moves on to other work. Pending questions are also listed in the planner prompt with instructions not to re-ask.

ask_human Protocol

src/tools/ask-human.ts · config.askHuman
Limits chosen from ten days of inbox data (27 asks, 20 closed unanswered): every ask that got an answer was at or under 600 characters and asked exactly one thing.
askHuman: {
  maxChars: 600,        // questions longer than this are rejected with guidance
  autoCloseHours: 72    // pending asks older than this are auto-closed
}

Ask-Permission Flow

The AskPermissionStore enables agents to request human approval before performing sensitive actions during autonomous operation. Unlike ask_human (free-text answers), permission requests receive binary decisions: approved or denied.

AskPermissionStore

Persistence

Pending, resolved, and history entries are all persisted to data/ask-permission/history.json. On restart, pending requests are restored with fresh deferred promises. This means permission requests survive dispose() and process restarts.

Allowed Write Paths

Each bot can configure allowedWritePaths (default: ["productions/"]). Writes to these paths do not require ask_permission. The planner prompt explicitly lists which paths are allowed and which require permission.

Flow

StepDescription
1. RequestAgent calls ask_permission tool. AskPermissionStore.request() registers the request, persists to disk, and returns a promise.
2. DisplayPermission request appears in the web dashboard permissions page with action, resource, description, and urgency.
3. DecideHuman approves (approveById()) or denies (denyById()). Promise resolves with the decision.
4. ConsumeNext agent loop cycle calls consumeDecisionsForBot(). Permission decisions are injected into the planner context.

Karma Outcomes & Trait Policy

Two evolution levers were re-based on outcomes in August 2026. Karma used to be mostly activity — every non-repeated cycle earned a credit, so a bot that produced a lot and was read by nobody outscored one the operator actually answered — and the strategist prompt prescribed a universal trait direction for low engagement, which slowly turned a reactive watchdog into a sociable one.

De-biased strategist guidance (agent-loop-prompts.ts)

  • "No change" is the expected answer most cycles — omit trait_adjustments or send {}. Traits describe who the agent is, not a lever for short-term engagement numbers.
  • Every delta must cite a concrete observation from this agent's recent actions or outcomes (a named action, a repeated error class, an explicit operator request, a rejected production), named in reflection.
  • Identity consistency: a reactive, guardian, watchdog or monitor identity must not drift toward higher sociability or lower independence because engagement is low — low engagement with no users is evidence about the audience, not the trait. There is no universal direction.
  • Patterns that do count: the same tool error class repeating (caution up / risk_tolerance down), work rejected as shallow (depth up), a confirmed behavioural rut (curiosity up), an explicit operator request for more or less outreach (sociability accordingly).
  • Locked or pinned traits listed in the trait state are not to be proposed.

Scheduling

Scheduling logic lives in agent-scheduler.ts as the AgentScheduler class. Each bot maintains its own BotSchedule object that tracks execution state, strategist timing, and recent activity history. Bots with agentLoop.enabled: false are skipped during syncSchedules() and syncBotLoops() — the per-bot toggle allows disabling the agent loop for specific bots while keeping it globally enabled.

Immediate Run & Pending Wake

requestImmediateRun(botId) triggers an agent loop cycle as soon as possible for a specific bot. This is called automatically after every user conversation completes (via the MessageBuffer callback in BotManager), ensuring the bot acts on user requests without waiting for the next scheduled cycle.

Behavior

Bot StateAction
Idle (not executing)Sets schedule.nextRunAt = Date.now() and calls wakeUp() to abort the current sleep, causing the bot loop to run immediately.
Busy (executing)Adds botId to a pendingWakeRequests Set. When the current cycle finishes, runBotLoop() checks and consumes the pending wake, skipping the inter-cycle sleep.

Design Decisions

  • Set, not queue: Multiple requests for the same bot coalesce into one pending wake. The planner sees all recent conversation context on re-run.
  • Fire-and-forget: The conversation pipeline does not await the agent loop. Response latency is unaffected.
  • No LLM classification: Every user message triggers a wake. The planner already decides if there's actionable work (returns priority: none cheaply if not).

Graceful Stop (Draining)

AgentScheduler.gracefulStop(timeoutMs?) enables safe shutdown: it sets a draining flag, wakes all sleeping bots, and waits for executing cycles to finish (or timeout). The runBotLoop() and runLoop() guards check !this.draining, so sleeping bots exit immediately while executing bots finish their current cycle before exiting. After all loops settle, stop() runs for full cleanup.

Standing Directives

Operators can assign standing directives to individual bots — ongoing behavioral instructions that are injected into strategist, planner, and executor prompts via a dedicated "Operator Directives" section. Unlike goals (which the agent manages), directives are operator-controlled and persistent.

Config fields (BotAgentLoopOverrideSchema):

  • directives: string[] — custom free-text directives (max 10, 500 chars each)
  • presetDirectives: string[] — IDs of built-in directive bundles (e.g. "conversation-review")

resolveDirectives(botConfig) in agent-scheduler.ts merges custom directives with expanded preset definitions from PRESET_DIRECTIVE_DEFINITIONS in agent-loop-prompts.ts. The result is passed to all prompt builders and rendered by buildDirectivesSection().

API: GET /api/agents/:id/directives returns directives, presetDirectives, resolvedDirectives (expanded), and availablePresets.

Retry on Error

Retry logic lives in agent-retry-engine.ts. When executeSingleBot() returns an error, executeSingleBotWithRetry() checks if the error is transient (timeout, network, rate limit) via isRetryableError(). Permanent errors (auth, permission) skip retry entirely. Each retry gets a fresh maxDurationMs budget.

Error classification order (classifyError())

2026-08-22 A Claude CLI rate limit used to classify as PERMANENT: the CLI's JSON error blob contains "permission_denials":[], and the substring permission matched the PERMANENT pattern list before the CONTEXTUAL check ever ran. A 429 therefore skipped retry entirely and never fed the circuit breaker. Classification now runs in this order:

StepInputResult
1. Structured signalsapiErrorStatus / resetsAt off a ClaudeCliError429 → CONTEXTUAL (carrying resetsAt), 401/403 → PERMANENT, 5xx → TRANSIENT; anything else falls through
2. Failover reasonstatusCode / Node code on non-string errorsPre-existing structured path, unchanged
3. Word-anchored patternsThe message with JSON keys stripped ("key": removed)PERMANENT → CONTEXTUAL → TRANSIENT, as before — a permission word in real prose still classifies as PERMANENT

ClassifiedError gained resetsAt?: Date.

Retry Config

// agentLoop.retry (global or per-bot override)
{
  maxRetries: 2,          // default: 2 (3 total attempts)
  initialDelayMs: 10000,  // default: 10s
  maxDelayMs: 60000,      // default: 60s cap
  backoffMultiplier: 2    // default: exponential x2
}

Backoff Formula

delay = min(initialDelayMs * multiplier^attempt, maxDelayMs) ± 20% jitter. The jitter prevents thundering herd when multiple bots fail simultaneously.

Side-Effect Suppression

During intermediate retries, logToMemory() and sendReport() are suppressed via the suppressSideEffects option. Only the final attempt (success or last failure) writes to memory and sends reports.

Schedule Tracking

BotSchedule tracks retryCount and lastErrorMessage. Both reset to zero on success. The dashboard displays retry count in the bot schedules table and shows a retry attempt badge in the last results table.

Backend Circuit Breaker

A 429 on Ollama Cloud is a shared quota, so one bot's failure predicts every other bot's. Before the breaker, a quota outage cost every bot three retries per cycle and an [ERROR] line per attempt in its daily memory. BackendCircuitBreaker (in agent-retry-engine.ts, one instance per AgentLoop) is keyed by LLM backend and applies to the planner/strategist path.

Config

// agentLoop.circuitBreaker
{
  enabled: true,
  threshold: 3,                    // consecutive CONTEXTUAL (429 / quota) failures before the circuit opens
  cooldownMs: 1_800_000,           // 30 min for an ordinary rate limit
  weeklyQuotaCooldownMs: 21_600_000 // 6 h when the error text says "weekly usage limit"
}

State Machine

EventEffect
CONTEXTUAL failurerecordFailure() increments the consecutive count; at threshold the circuit opens until now + cooldown.
Other failureThe backend answered, just not with a quota error: the consecutive run resets and the circuit closes.
SuccessrecordSuccess() closes the circuit and forgets past failures.
Cycle start while openshouldSkip() returns skip: true; executeSingleBot() returns status: 'skipped', skippedReason: 'circuit-open:<backend>' with a single info log, zero duration and no memory write.
Cooldown elapsedHalf-open: exactly one caller is granted a probe (probe: true); everyone else keeps skipping until it reports. A probe that never reports expires after PROBE_TTL_MS (10 min) so a crashed cycle cannot lock a backend out.
Failure mid-retryexecuteSingleBotWithRetry() checks isCircuitOpen() after every failed attempt and stops the retry ladder at once (retryCount reset, lastErrorMessage kept).
MemoryWhile the circuit is open the [ERROR] daily-memory line is suppressed — one line per outage is plenty.

Cooldown from the backend's own reset hint

2026-08-22 When the classified error carries resetsAt — parsed by parseResetsAt() from the Claude CLI's resets 12:20pm (zone) hint — the cooldown ends at that instant instead of a fixed cooldownMs, clamped to [BackendCircuitBreaker.MIN_RESET_COOLDOWN_MS (60 000 ms), weeklyQuotaCooldownMs]. Without a hint the behaviour is unchanged: weeklyQuotaCooldownMs when isWeeklyQuotaError() matches (/weekly usage limit/i), cooldownMs otherwise.

Daily-memory error memo

The breaker collapses quota outages, but a PERMANENT failure — expired credentials, say — deliberately does not open the circuit, so it recurred on every cycle and appended the same [ERROR] line to the bot's daily memory each time. AgentLoop now keeps a per-bot memo of the last recorded error and consults the pure helper shouldRecordErrorInMemory(last, message, now, windowMs) (agent-loop-utils.ts, ERROR_MEMO_WINDOW_MS = 6 h) before writing. An identical message inside the window is skipped; a different one is always recorded.

Introspection

AgentLoop.getCircuitState() and BotManager.getAgentLoopCircuitState() return Record<backend, { open, halfOpen, until, consecutiveFailures, lastError }>. skippedReason is also surfaced on BotScheduleInfo.
