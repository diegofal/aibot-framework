Operator API

The Operator API provides programmatic control over bots without requiring a chat channel (Telegram, WhatsApp, etc.). It enables triggering skill commands, inspecting bot capabilities, and automating operations via HTTP.

Authentication

The skill-command endpoints live under /api/agents/; the read-only telemetry and maintenance endpoints below live under /api/stats/ and /api/hygiene/. All are protected by the existing tenant auth middleware. Include your API key in the Authorization header: 

Authorization: Bearer YOUR_API_KEY

Endpoints

List Bot Skills & Commands

GET /api/agents/:botId/skills

Returns all loaded skills for a bot, including available commands.

Response

{
  "botId": "default",
  "skills": [
    {
      "id": "reflection",
      "name": "Reflection",
      "version": "1.0.0",
      "description": "Self-reflection on recent conversations",
      "commands": [
        { "name": "reflect", "description": "Run self-reflection on recent conversations" }
      ]
    }
  ]
}

Execute Skill Command

POST /api/agents/:botId/skills/:skillId/:command

Executes a skill command headlessly. The bot must be running and have the skill enabled.

Request Body (optional)

{
  "args": ["arg1", "arg2"]
}

Success Response (200)

{
  "ok": true,
  "result": "Reflection complete. Updated IDENTITY.md and journal.",
  "durationMs": 12345
}

Error Response (404 / 500)

{
  "error": "Bot default is not running",
  "durationMs": 2
}

Channel State on Agents & Status

GET /api/agents · /api/agents/:botId · /api/status

Every agent row carries channel, the outcome of the bot's last channel start (BotManager.getChannelState()), so an operator script can tell a revoked Telegram token from a bot that is headless on purpose. /api/status exposes the same per bot as bots.channels[].

Shape

{
  "kind": "telegram" | "headless",
  "state": "ok" | "revoked" | "placeholder" | "missing" | "error",
  "lastError": string | null,   // operator-facing cause for revoked / error
  "checkedAt": string | null    // ISO; null when derived from config alone
}
StateMeaning
okTelegram polling is up
revokedReal-shaped token, Telegram answered 401 — rotate it in BotFather
errorReal-shaped token, start failed for another reason (409 duplicate consumer, API unreachable); see lastError
placeholderA string that cannot be a token ("nothing", the bot id). Never sent to Telegram; bot runs headless
missingEmpty or null token (null is the explicit "headless on purpose" value)
nullNever started and the token is real-shaped — only Telegram can say

Stats & Behaviour

GET /api/stats/fleet?window=24h|7d|30d
GET /api/stats/bots/:botId?window=
GET /api/stats/behaviour?window=
GET /api/stats/infra

Read-only aggregations over the on-disk telemetry (src/stats/): per-bot posture, LLM and tool counts, outputs and reviews, ask engagement, goals, karma, trait drift, soul health; cross-bot behaviour views; backend / cron / Telegram / log health. Tenant-scoped, cached 60 s, never throws on missing data. Response types are frozen in src/stats/types.ts. Full field list on the Web Dashboard page.

Posture (first matching rule wins)

PostureRule
dormantenabled: false
unknownthe agent loop never ran for this bot
blockedretrying with an error (retryCount ≥ 3) or every active goal is blocked
idleno active goals
standby≥ 5 consecutive idle cycles, last run older than 3 days, or no production outcome in 48 h with an idle streak
activeotherwise

Hygiene Routines

GET /api/hygiene/routines
POST /api/hygiene/run
GET /api/hygiene/history?botId=&limit=

Deterministic maintenance without an LLM. Preview writes nothing; apply backs up and never deletes (soul files to .versions/<file>.<ISO>.bak, cleanup into data/_trash/<stamp>/ with manifest.json). Bot routines need a botId visible to the tenant; data-cleanup and the fleet half of all are admin-only.

Request Body

{
  "routine": "goal-lint" | "soul-structure" | "memory-hygiene" | "productions-triage" | "data-cleanup" | "all",
  "botId": "default",          // required for bot-scoped routines
  "apply": false,              // default false = preview
  "options": { "archiveStale": true, "staleDays": 7 }   // routine-specific, optional
}

Response (HygieneRun)

{
  "runId": "…", "routine": "goal-lint", "botId": "default", "dryRun": true,
  "startedAt": "…", "finishedAt": "…",
  "findings": [
    { "id": "goal-lint:archived-in-active:0", "kind": "archived-in-active", "severity": "warn",
      "file": "GOALS.md", "line": 12, "message": "…", "fixable": true,
      "fix": { "action": "move-to-completed", "details": "…" } }
  ],
  "applied": [], "skipped": [], "backups": []
}

Error Cases

ErrorStatus
Invalid JSON / missing routine / unknown routine / missing botId400
Bot not found (tenant scope)404
Fleet routine from a non-admin tenant403
Routine threw while running200 with error set on the run

Example

curl -X POST http://localhost:3000/api/hygiene/run \
  -H "Authorization: Bearer $API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"routine": "memory-hygiene", "botId": "default", "apply": false}'

Karma Score Composition

GET /api/karma/:botId · /api/karma

Karma is outcome-based: each event is an outcome kind whose delta comes from config.karma.rewards. breakdown shows what the score is made of over the trailing 30 days (raw, undecayed sums), so an operator script can tell activity karma from outcome karma.

Response excerpt

{
  "botId": "default",
  "current": 57.4,
  "trend": "rising",
  "recentEvents": [ { "delta": 2, "source": "engagement", "kind": "askAnswered", "reason": "…" } ],
  "breakdown": {
    "windowDays": 30,
    "bySource": { "production": 6, "engagement": 5, "tool": -3 },
    "byKind":   { "productionApproved": 6, "askAnswered": 2, "humanReply": 3, "toolError": -3 }
  }
}

Score composition (defaults)

Outcome kindDeltaSourceWhen
productionApproved+3productionOperator approves a production
productionRejected-1productionOperator rejects a production
askAnswered+2engagementA human answers an ask_human question
humanReply+3engagementA human replies to the bot — max once per bot per 6 h (karma.humanReplyCooldownHours)
toolError-1toolA tool call fails
novelAction0agent-loopA non-repeated cycle (off by default; a 0 reward writes nothing)
collaborateCompleted0agent-loopCollaborationManager.initiateCollaboration() completes a session (not on timeout). Worth 0 by default, so nothing is written until an operator raises it

Tenant Isolation on the Chat API

POST /api/v1/chat/:botId · GET /api/v1/chat/:botId/history

Security fix 2026-08-22 Both routes guarded access with c.get('tenantId') — a context key nothing ever sets. The tenant auth middleware stores a TenantContext under tenant, so the guard read undefined, the comparison never ran, and in multi-tenant mode an authenticated tenant could chat with and read the full history of another tenant's bot.

Both now use the shared helpers from src/tenant/tenant-scoping.ts — getTenantId(c) (which reads tenant) and isBotAccessible(botConfig, tenantId) — and answer 404 for a bot outside the caller's tenant. An admin context (__admin__) and single-tenant mode are unaffected. Regression test: tests/web/routes/chat-tenant-isolation.test.ts.

Related, in the same pass: GET /api/agent-loop/llm-stats filtered BotManager.getLlmStats() — an array — with Object.entries() and matched the keys against the caller's bot ids. The keys were array indices, so every non-admin tenant received an empty result. It failed closed, but it failed; the route now filters the array on botId.
