Fleet Watcher

One always-on workspace per fleet, in the same process as the bots (src/watcher/). The bots stay on cycles as specialists; the watcher senses every event, keeps what matters as neurons in a graph, integrates across bots, broadcasts back, and keeps a self-model it can be asked about. Off by default: watcher.enabled, and each LLM tier has its own switch (notice.enabled, integrate.enabled). Plans: docs/plans/watcher-consciousness-plan.md (design and metrics) and docs/plans/watcher-implementation-plan.md (build order and deviations as built).

Back to the bots

  • Broadcasts (broadcast.ts, broadcasts.jsonl) — wake (run the next cycle now), directive (curiosity directive, source watcher), goal (written to GOALS.md, actor watcher), question (to the operator through send_proactive_message). At most 3 per bot per UTC day and one per insight and kind. The planner shows them as ## Fleet broadcast; the plan names one in serves_broadcast and the cycle row records broadcastIds / servesBroadcast.
  • fleet_memory_search — bots query the graph. Neurons supported by an operator message (meta.operatorSourced) are shown only to the operator. On an operator turn only, the conversation prompt also gets “## What the fleet knows” (same ranking, top 5, supporting bot named) and a hint to call the tool.
  • ## Your current state (phase 4) — in both planner prompts and the conversation system prompt while the watcher runs: the bot's live phase, tool and since (from the watcher's own presence tracker), its running cycle (goal and plan), and what the fleet is attending to (never operator-sourced neurons).

Fast lane (fast-lane.ts, O1 of docs/plans/watcher-optimizations-plan.md): right after a notice pass, a pattern it created or recognised (or a fact at confidence high) that two or more bots support (a recognition adds the pass's bots to the support, so two bots in different passes qualify on the second; never one an operator message supports, nor an operator-sourced fact) goes at once, as a directive, to every enabled non-tenant bot outside that support that relates to it (a related edge to one of its neurons, or the pattern names a tool it used in the last 7 days). Same Broadcaster, caps and records as integrate, source: 'fast-lane', one per target bot, at most watcher.fastLane.maxPerDay (6) a day; never a question, goal or wake. The next integrate prompt shows it next to the pattern ("fast lane"), so Opus does not resend it, and metric 6 splits fast lane from integrate.

Stakes (O3)

Interoception shapes what the watcher does, not only what it says (src/watcher/stakes.ts, pure; the watcher computes stakes() at most every 30 s or when the operator writes). Budget pressure: a tier with 75 % of today's budget used (calls, and tokens for integrate) wakes at twice its wakeSalience. Operator silence: silent more than 48 h, a question broadcast is held (row integrate:question-deferred, whyNoBroadcast: "operator silent"; the insight stays on the agenda; deferredQuestions in integrate.json) and goes out as soon as the operator writes (integrate:question-released). Breaker open: the tier whose backend's breaker is open sleeps (no Ollama fallback client exists yet). Fleet karma falling 5 points below its 24 h peak (stakes.json): the next integrate prompt opens with ## Something is wrong. A rule that starts firing logs one stakes:<rule> row, and the fired rules of a tier go on its pass row's drivenBy (and the integrator's, so introspection can name them as a cause).

Operator controls (autonomy rungs 0 and 2)

Plan: docs/plans/watcher-autonomy-plan.md. The operator's control is an invariant enforced in code. Hard kill (src/watcher/kill.ts): AIBOT_WATCHER_KILL=1 or a <paths.data>/watcher-kill file refuses every model call inside instrumented(), the single choke point (a contract test forbids any other watcher module from importing an LLM client), stops a running watcher and refuses start() (the route answers 409). Monthly ceiling: watcher.autonomy.monthlyCeilingUsd (90), summed from the budget files. Proposals (src/watcher/autonomy/, off by default): data over an allowlist of bounded tunables (locked.ts); anything else is rejected-locked at parse; at most 3 pending; approval only from the admin dashboard, bound to the content hash, 72 h expiry; every applied change keeps its before-values (self/changes.jsonl), can be reverted, and is rolled back by the hourly tick when its guard metric regresses (a rollback whose write failed is retried at every tick while its guard still breaches, inside or past its window; a change whose live values are neither the old nor the new ones waits for the operator's Accept current values, which ends it accepted with what was live and writes nothing). GET /proposals writes nothing: expiry shows as it reads now and the tick stores it. Page: kill banner, month spend, Proposals panel; Needs You lists pending proposals for admins.

Self-study (rung 2) (src/watcher/autonomy/self-study.ts, off by default: watcher.autonomy.selfStudy.enabled and proposals.enabled both on). Once a week (everyHours 168; the first run firstRunDelayMinutes 30 after the watcher starts) code builds a fleet cost digest of the last 7 days from records: per non-tenant bot, USD and calls by caller (LLM query log), cycle status counts with code-derived error classes and up to 5 sample error cycle ids (cycle log), failing tools by name and failureKind (tool audit), its agentLoop.every; fleet totals; the watcher's own spend by tier (budget files). Numbers, ids and code names only: never a plan, summary, message, tool argument or error text; at most 6000 chars. One notice-tier call through instrumented() (caller watcher:self-study: kill, ceiling and daily cap apply) sees only the digest and the allowlist with live values: no tools, no network. Its answer (≤ 3 proposals, ≤ 5 findings) is checked by code before the store sees it: every support id must be one the digest showed (else the proposal is dropped with a self-study:dropped row), from is stamped with the live value, proposedBy is watcher; then the rung 0 parser refuses locked paths and out-of-range values. self/NOTES.md (≤ 4000 chars) and self/self-study.json are written by code; a refused or failed attempt retries after 6 h; a stop during the call discards the answer and writes nothing. Rows self-study:run / skipped / failed / dropped. Page: a Self-study card under Proposals with the last and next run, the notes and a two-click "Run now".

Roster (on by default)

src/watcher/roster/, watcher.roster { enabled: true, everyHours: 168, maxProposals: 2, maxPending: 2 }. Plan: docs/plans/mind-roster-plan.md. The operator writes a brief on the watcher page (≤ 5 wants: what, how often, how delivered, what good looks like, plus notes; self/brief.json). The designer (caller watcher:roster, the integrate tier or else notice, through instrumented()) reads the brief, every bot, what each bot it proposed did since approval (completed cycles, productions created / approved / rejected), its earlier proposals, the presets and its own state, and answers with bots to propose, bots of its own to retire and questions. Code vets every bot: it serves at least one want, has a valid untaken id, a cadence in 30m–7d, a known preset, a deliverable and a kill criterion; at most maxProposals per run and maxPending waiting. What passes becomes an agent proposal with proposedBy: '__watcher__'; approving it creates the bot off, with its goals in GOALS.md as the operator's and its preset's disabled tools. Due 30 min after a changed brief, then every everyHours; a refused attempt retries after 6 h; a stop during the call writes nothing. State in self/roster.json; rows roster:brief / run / dropped / failed / unparsable.

Mind reset (scripts/watcher/reset-mind.ts, src/watcher/reset.ts), offline with the container stopped: every bot enabled: false and <data>/watcher moved to <data>/_trash/<stamp>-mind-reset/ with a manifest; --restore puts both back. Birth reads only enabled bots' people, goals, knowledge, memory and history (the fleet stage still lists every bot), so the next start is a fresh graph.

Self-improvement (on by default)

src/watcher/self-improve.ts, watcher.selfImprove { enabled: true, toolProblemBots: 3, everyHours: 24 }. Plan: docs/plans/self-improve-plan.md; the bot side is in Agent Loop. Checked hourly, run every everyHours while the watcher runs. Over every enabled, non-tenant bot's last 7 days of tool audit: a named failure class present (≥ 2 failures) in toolProblemBots bots is a tool problem — a log row, a Needs You item (kind watcher, admin only) and a suppression in the LESSONS.json of every bot whose loop is on, so no bot learns to work around a bug; other:* classes never count. A proven own lesson is lent to other bots whose loop is on and that show the same class (once per bot and class in 7 days), measured on its own there. State in self-improve.json (last, dismissed). The weekly self-study digest gains per-bot lesson counts and the tool-problem keys (code names only). Routes: GET / POST /api/watcher/self-improve, POST /api/watcher/self-improve/tool-problems/:classKey/dismiss.

Records and upkeep (optimizations O5–O7). Every call instrumented() sends to a model (notice, integrate, introspect; answered or failed, never an aborted one) leaves a pass record in passes/ (src/watcher/pass-records.ts): the system and user prompt with every line clipped to 300 chars, the response, model, tokens, cost and the cycle ids the prompt named, so "why did it decide that" is read, not inferred. GET /api/watcher/passes lists them and /passes/:id returns one; the page's "What it saw" fold under a pass row finds its record by caller, exact duration and end time (the log row does not carry the id). The hygiene routine watcher-graph cleans the graph through the running watcher, never its files: it archives birth facts that are bookkeeping lines or bare date headers and merges one bot's near-duplicate facts (similarity ≥ 0.9, never two that differ in a negation or a number/date) into the newest with Graph.mergeInto; nothing is deleted ("Clean the graph" on the page, never part of all). GET /api/stats/infra probes the embedding service (one embed, cached 5 min) and the page header shows "embeddings: ok" or "down since …".

Forgetting and consolidation (optimization O10). The watcher forgets by importance, not by age. src/watcher/importance.ts scores every neuron from what is already recorded — use (activations, half-life 14 days) 0.25, consequence (it supports an insight, a resolved prediction or a broadcast a cycle served) 0.35, breadth (distinct bots plus related links, log-scaled) 0.15, surprise 0.10, the operator's 👍/👎 0.15 — and writes the reason in words. Agents, people, goals, anything with 👍, what a served broadcast stands on and anything younger than forget.graceDays are never forgotten. The daily maintenance archives every neuron under forget.threshold that is past the grace and not protected, lowest first and at most forget.maxPerRun (200) a run, whatever the size of the graph; above graph.targetNeurons (8000) it goes past that batch until the target is reached; each one leaves meta.archivedReason (the Why panel's "Why archived"); one that fires again comes back and is counted as returned. Once a night at consolidate.hour, and only while no agent-loop cycle runs, src/watcher/consolidate.ts takes connected clusters of related, low-importance facts of one provenance class and asks the notice model (its budget, one call per cluster) for a short summary neuron; the facts are folded into it with Graph.mergeInto. A summary of operator material stays operator material. Metric 5 counts archived, returned, consolidated and summaries; the graphSize guard watches the live count.

Predictions are judged against the ground truth. When a prediction falls due, src/watcher/outcomes.ts shows the judge (notice tier) the tool audit and cycle log of the bots it names (all bots when it names none) between createdAt and dueAt, at most 60 lines, plus the watcher's own rows; the answer is happened, did_not_happen or unknown. A prediction that states an absence ("makes no …") happened when the records show the absence. Nothing recorded about the named bots is unknown without a call. An unknown is final and never scored: calibration (metric 4) counts it apart.

Scripts

  • bun scripts/watcher/baseline.ts — the phase 0 baseline report.
  • bun scripts/watcher/canary.ts — plant a fact through one bot (addressed once by its display name, --name or GET /api/agents/:id), check recall through another: plant requires --expect <word> and check passes only when the answer names every expected word.
  • bun scripts/watcher/rejudge.ts [--apply] [--limit N] — one-off: judge the already-resolved predictions again with the ground-truth judge; dry run by default, --apply (watcher stopped) writes the new outcome plus meta.rejudgedAt and meta.previousHappened.
  • bun scripts/watcher/tenant-paths.ts [--config …] [--json] — assessment only (O8): per bot and data-path site, the path resolved today (any tenantId) against isTenantBot; changes nothing.
  • bun scripts/watcher/introspect.ts --bot <id> or --subject watcher — ask and score; appends introspection.jsonl (the watcher route appends server-side).
