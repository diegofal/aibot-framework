### Relays: person-to-person messages through a bot, both ways (branch `feat/relay`)

- **What.** Finny told a user it had passed her question to the operator; `send_message` had hit two "Diego" contacts, retried on the web one, and the web delivery only appended to the shared anonymous widget session (`private:0`) while returning "Message sent". Nothing could route an answer back, and Telegram users were never in the directory. Now (`src/relay/`): every Telegram speaker is tracked, the operator is one seeded contact (`config.operator`), `send_message` creates a durable relay with the sender injected by the executor (`_requester`), delivers Telegram (own instance → fleet, 403 falls through) → WhatsApp → web, and reports `delivered | queued | failed` honestly. A Telegram reply to a relay message goes back to the requester with no LLM turn; free-text answers close with `send_message replyTo`; both chats' prompts list the relays and their status. Policy: anyone ↔ operator; person ↔ person behind `bots[].relay.peerToPeer`. Also: `ask_human` no longer messages a non-operator's chat nor swallows their next message; conversation tool calls reach the tool audit. Compared with OpenClaw (`conversations_turn`, delivery states), which has no person-addressed relay and a 300 s in-memory reply waiter. Plan: `docs/plans/relay-plan.md`.
- **Status.** Implemented in worktree `../aibot-relay`; not committed, not deployed.
- **Verified by.** Lint + typecheck clean; `bun test` 6793 pass / 1 fail (`tests/session-end.test.ts` time-of-day test, fails on main too after ~21:00). End-to-end relay tests with mocked Telegram both directions (`tests/relay/e2e.test.ts`). Not yet tried live.
- **Open.** The anonymous widget sessions all share `bot:<id>:private:0`: earlier web "sends" to the operator sit in a transcript every widget visitor replays (technical-debt entry). The question sent before this change is not a relay, so it will not route back. No live web presence check; Discord outbound; unbacked-promise detector.
