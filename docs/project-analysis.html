Veredicto general El framework es arquitectónicamente sólido y muy completo (41 tools, 15 skills, multi-tenant, A2A, MCP, export/import, agent loop, failover, etc.), pero la instancia en producción está medio rota: el auto-start está desactivado por env, el único bot que corre es default, la API key de Ollama Cloud está revocada (HTTP 401 en todos los modelos), el CLI de Claude no está instalado en la imagen, y dos MCP servers (npx, uvx) llevan 4.122 intentos de reconexión saturando el log. Resultado: el bot default hace polling de Telegram pero cualquier mensaje que requiera LLM va a fallar o caer al fallback, y el agent loop está prácticamente inactivo.

El proyecto no es un MVP: es un framework maduro con documentación extensa, tests en casi todos los módulos, convenciones claras y un grafo de dependencias bien definido (ver CLAUDE.md). El problema es operacional, no estructural.

2. Qué entendí del proyecto

AIBot Framework es un orquestador de agentes autónomos con personalidad persistente. Cada bot tiene:

  • Soul files — IDENTITY.md, SOUL.md, MOTIVATIONS.md, GOALS.md + MEMORY.md consolidado + daily logs en soul/<botId>/memory/.
  • Memoria semántica RAG — SQLite con vector + FTS5, decay temporal exponencial, indexado de transcripts al boot.
  • Agent loop — patrón planner→executor con strategist, retry con backoff, detección de idle y novelty enforcement.
  • Skills — 15 bundled (reflection, intel-gatherer, improve, calibrate, humanizer, phone-call, mcp-client, daily-priorities, daily-briefing, quick-notes, reminders, task-tracker, reddit, calendar, example). Plugin system con skill.json y SKILL.md declarativo.
  • Tools — 41 LLM-callable tools en 11 categorías (web, files, exec, soul/memory, goals, collaboration, cron, social, calendar, core-memory, permissions, productions, MCP).
  • Multi-canal — Telegram (grammy), WhatsApp Cloud API, Discord (REST + Gateway WS), REST, WebSocket widget. Outbound factory para mensajes proactivos.
  • Multi-tenant BaaS — 6 fases: auth, config isolation, data isolation (data/tenants/{tenantId}/bots/{botId}/), quota + rate limit, onboarding + billing Stripe, per-user isolation.
  • Colaboración bot-a-bot — 3 modos: visible, internal, delegation + multi-turn sessions + collaboration-safe tool filtering.
  • MCP bidireccional — client (conecta a servers externos) + server (expone tools a Claude Desktop/Cursor) + tool-bridge para Claude CLI.
  • A2A Protocol v0.3.0 — JSON-RPC server, agent directory con heartbeat, task store, client pool, skill→tool adapter.
  • Failover de modelos — cadena ordenada con cooldown, clasificación de errores (auth/billing/rate/timeout/context/format), clamp al context window más chico.
  • Seguridad — audit on startup (24h cooldown), security audit module, secret redaction en export (${VAR}), config-sanitizer.ts como frontera.
  • Lifecycle hooks — 8 eventos EventEmitter (message_received/sent, before/after_llm_call, before/after_tool_call, before_compaction, agent_loop_cycle).
  • Dashboard web — Hono + SPA con 17 páginas (Dashboard, Agents, Sessions, Conversations, Cron, Tools, Tool Runner, Skills, Activity, Permissions, Inbox, Productions, Karma, Agent Proposals, Agent Feedback, Integrations, Settings).

Arquitectura del core (src/bot/)

El core es un facade BotManager que compone ~42 módulos enfocados, todos recibiendo un BotContext compartido por referencia. Las dependencias circulares (collaborate/delegate → CollaborationManager) se resuelven con lazy callbacks () => collaborationManager. El grafo completo está en CLAUDE.md y es coherente.

Canal de mensaje típico

InboundMessage (Channel adapter)
  → ConversationGate (auth / grupo / bot-to-bot / ask_human)
  → GroupActivation (relevance check en grupos)
  → TopicGuard (LLM pre-filter, opcional)
  → ConversationPipeline
      ├─ session expiry
      ├─ RAG prefetch (MemoryManager)
      ├─ ContextCompactor (si cerca del límite)
      ├─ SystemPromptBuilder (conversation | collaboration)
      ├─ LLM call (FailoverLLMClient → Ollama | Claude CLI)
      ├─ ToolExecutor (con hooks + retry + loop detection)
      ├─ persist (SessionManager + LlmQueryLog)
      └─ reply (Channel.send + streaming + edit progresivo)

Agent loop

AgentScheduler (cron/continuous) 
  → AgentPlanner (LLM: ¿qué hago ahora?) 
  → AgentStrategist (goal reflection, cadence) 
  → ToolExecutor (executa el plan con tools)
  → AgentRetryEngine (backoff exponencial, error classification)
  → AgentLoopUtils (digest, dedup, novelty check)

Topología

Dos containers via docker-compose.yml:

Dockerfile (multi-stage)

  • Stage 1 deps: oven/bun:1.3.11-slim + bun install --frozen-lockfile --production con PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1.
  • Stage 2 runtime: copia solo node_modules, src/, web/, scripts/ y config templates. COPY . . deliberadamente evitado para que config/config.json, .env, data/ y productions/ nunca entren en la imagen.
  • Usuario no-privilegiado bun (uid 1000), VOLUME ["/app/config","/app/data","/app/productions"].
  • ENTRYPOINT exec form → bun es PID 1 y recibe SIGTERM directo → graceful shutdown.
  • Block de Chromium comentado (Playwright opcional, +500 MB).

Compose

  • replicas: 1 — correcto: Telegram long-polling permite un solo consumidor por token (HTTP 409 si hay dos).
  • ports: 127.0.0.1:3000:3000 — bind a loopback a propósito (single-tenant no tiene auth en /api/*). Acceso via SSH tunnel.
  • init: true — reapa zombies de subprocesos tar/claude.
  • stop_grace_period: 30s — espacio para stopAll → cron stop → session dispose.
  • logging: json-file max-size:10m max-file:3 — rota stdout del container (pero no rota data/logs/aibot.log).
  • Ollama sidecar detrás de profiles: ["local-ollama"] — opcional desde que existe auth directa a Ollama Cloud.
  • OLLAMA_BASE_URL: ${AIBOT_OLLAMA_URL:-http://ollama:11434} — override explícito para no heredar OLLAMA_BASE_URL=127.0.0.1 del .env del host.

Entrypoint (docker-entrypoint.sh)

Idempotente: siembra config.json, bots.json y sources.yml desde /app/config-defaults/ solo en first boot. Nunca sobrescribe un archivo existente (el volumen es runtime-mutable). Imprime un banner explícito en fresh install avisando que todos los bots arrancan enabled:false.

Variables de entorno observadas (dentro del container)

OLLAMA_BASE_URL=http://ollama:11434       ← apunta al sidecar, NO a Ollama Cloud
OLLAMA_API_KEY=ff836c...<32 chars>...      ← presente pero RECHAZADA (HTTP 401)
AIBOT_AUTOSTART_BOTS=false                 ← auto-start DESACTIVADO por env
ADMIN_API_KEY=<no seteada>                  ← middleware admin fail-closed → 503
Discrepancia config.json vs env El config/config.json en el repo local dice "baseUrl": "http://127.0.0.1:11434" (loopback, para bare metal), pero dentro del container el JSON dice "${OLLAMA_BASE_URL}" y el env overridea a http://ollama:11434. El sidecar de Ollama está corriendo pero la API key configurada es para Ollama Cloud, no para el daemon local. El daemon local no espera auth → el header Authorization: Bearer ... que se le manda hace que el proxy interno responda 401. El sidecar local + API key cloud son incompatibles: o se saca la key y se usa el daemon local, o se cambia OLLAMA_BASE_URL=https://ollama.com y se saca el sidecar.

5. Qué cosas NO funcionan

1. Auto-start desactivado (AIBOT_AUTOSTART_BOTS=false) El env override desactiva el arranque automático. Solo default corre porque fue iniciado a mano desde el dashboard. Si el host reboot o el container se recrea, ningún bot levanta solo — hay que entrar al dashboard y empezar uno por uno. El log lo repite en cada boot: "Auto-start is DISABLED — no agent will be started at boot".
2. Ollama Cloud API key rechazada (HTTP 401) En cada boot: "OLLAMA AUTHENTICATION FAILED — the configured ollama.apiKey was rejected (HTTP 401/403). [...] Every LLM call will fail." Los 3 modelos (kimi-k2.6:cloud, gpt-oss:120b-cloud, nemotron-3-super:cloud) son :cloud → requieren auth contra Ollama Cloud. La key está revocada/expirada. Peor aún: OLLAMA_BASE_URL=http://ollama:11434 apunta al sidecar local, que no necesita auth, pero el cliente le manda el header Authorization: Bearer <key cloud> igual → el daemon local lo rechaza. Toda llamada LLM por Ollama va a fallar.
3. Claude CLI no instalado en la imagen Executable not found in $PATH: "claude" aparece en el log cuando el skill intel-gatherer intenta generar summaries. El Dockerfile no instala Claude CLI (es un binario externo que requiere setup + auth). 7 de los 16 bots tienen llmBackend: "claude-cli" como backend → todos sus agent loops y conversaciones van a fallar. El fallback a Ollama también cae en el punto 2.
4. MCP servers en loop infinito de reconexión mcp.servers tiene dos entries: Everything (comando npx) y linkedin-scraper (comando uvx). Ni npx ni uvx existen en la imagen (no hay Node, no hay Python/uv). Cada server reintenta cada 60s y lleva attempt: 4122. Esto genera 41.282 líneas de error MCP en el log (~70% del archivo) y ruido constante en stdout. El autoReconnect:true no tiene circuit breaker real.
5. Bots con token inválido pero enabled:true myfirstmillion (token:"empty"), moltbook (token:"moltbook"), milei-rocca (token:"milei-rocca"), selfimprove (token:"selfimprove"), openclone (token:"dasoifhafoih") están habilitados. Si se activara el auto-start, todos intentarían getUpdates y fallarían con 401 Unauthorized. Solo default, cryptik y job-seeker tienen tokens reales de Telegram.
6. Reddit API sin credenciales → 403 en todas las categorías El skill intel-gatherer loguea "Reddit rate limit (403), skipping: LocalLLaMA" para cada subreddit. reddit.enabled:false en config pero el skill igualmente los scrapea. Las credenciales en .env son placeholders.
7. Log interno sin rotación data/logs/aibot.log = 12 MB y creciendo. El logging.driver del compose rota el stdout del container, pero el file JSONL interno no tiene rotación propia. En producción always-on esto crece indefinidamente. docs/deployment-cloud.md lo menciona pero no hay un logrotate configurado en el container.
8. ADMIN_API_KEY no seteada Sin ADMIN_API_KEY, el admin middleware es fail-closed (503 en /api/admin/*). Esto bloquea operaciones administrativas programáticas aunque el dashboard session-auth funcione.
9. Soul migration incompleta para bots secondary En el log: "Soul files found in legacy config/ path — will be migrated on startBot" para default, y "Export: soul directory missing, exporting empty" para cryptik, job-seeker, myfirstmillion, openclone, moltbook, monetize. Los souls existen en config/soul/<id>/ (12 dirs) pero la migración a data/tenants/__admin__/bots/<id>/soul/ solo se dispara al hacer startBot. Los bots que nunca arrancaron no tienen soul migrado.
10. fileTools.basePath apunta a path host config.json tiene "basePath": "/home/diego/projects/aibot-framework" y "allowedPaths": ["/home/diego/openclaw"] — paths del host, no del container. Adentro del container esos paths no existen → file_read/file_write fallarían o escaparían del sandbox.
11. Skill duplicados en milei-rocca El array skills de ese bot lista task-tracker, daily-priorities, calendar, reddit dos veces. No es fatal (un Set lo deduparía) pero indica descuido en la edición del JSON.

7. Qué agregaría / mejoraría

Operacional (urgente, para que la instancia actual funcione)

  1. Decidir topología Ollama: o bien (a) OLLAMA_BASE_URL=https://ollama.com + key nueva + sacar el sidecar + soul.search.enabled:false (Ollama Cloud no tiene embeddings), o bien (b) OLLAMA_API_KEY= (vacía) + dejar el sidecar local + bajar modelos nomic-embed-text y un modelo de chat no-:cloud. Hoy es un mix roto de ambos.
  2. Instalar Claude CLI en la imagen o cambiar los 7 bots con llmBackend:"claude-cli" a "ollama". Si se instala Claude, meterlo en un stage del Dockerfile con su auth via env.
  3. Sacar o desactivar los MCP servers rotos: poner mcp.servers: [] o agregar enabled:false por server hasta que npx/uvx estén disponibles. Mejor aún: agregar un circuit breaker en McpClient que después de N fallos consecutivos con ENOENT abandone y loguee una sola vez.
  4. Activar auto-start: sacar AIBOT_AUTOSTART_BOTS=false del .env (o setear true) una vez que los tokens y el LLM funcionen. Para el cutover ya no aplica.
  5. Mover tokens a .env: en bots.json usar "token": "${TELEGRAM_BOT_TOKEN_DEFAULT}" etc. Rotar los tokens ya commiteados via BotFather.
  6. Setear ADMIN_API_KEY con openssl rand -hex 32.
  7. Rotación de aibot.log: agregar un logrotate en el entrypoint o un pino-roll, o al menos un truncate periódico. 12 MB no es crítico pero en 3 meses sin atención crece.
  8. Deshabilitar los 5 bots con token falso: poner enabled:false a myfirstmillion, moltbook, milei-rocca, selfimprove, openclone hasta que tengan tokens reales.
  9. Corregir fileTools.basePath: apuntar a /app o al workDir del bot dentro del container.

Arquitectura (mejoras de fondo)

  1. Circuit breaker en MCP autoReconnect: después de M fallos con el mismo error (ENOENT, ECONNREFUSED), pasar a un estado disabled con backoff exponencial largo (p.ej. 1h) y un endpoint del dashboard para re-habilitar manualmente.
  2. HEALTHCHECK en Dockerfile: HEALTHCHECK CMD bun -e "fetch('http://127.0.0.1:3000/api/status').then(r=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))" cada 60s.
  3. Endpoint /metrics Prometheus: counters de messages in/out, LLM calls por backend/model, tool calls, agent loop runs, MCP reconects, RAG queries. Permitiría alertar en Grafana.
  4. Redaction de PII en logs: un transport de pino que masquee tokens, emails, phone numbers antes de escribir a aibot.log.
  5. Validación de tokens al startBot: antes de arrancar el polling, un getMe para validar el token y fallar con un mensaje claro (401 token invalid) en vez de dejarlo en loop de retry.
  6. Schema validation de bots.json con Zod: hoy el JSON se carga sin validar que los tokens no sean placeholders ni los skills existan. Un schema que rechace token:"empty" o skills duplicados habría evitado varios de los issues arriba.
  7. Graceful shutdown del MCP pool: en SIGTERM, además de stopAll, cerrar los stdio transports de MCP para que no queden zombies.
  8. Perfil Docker slim sin Ollama sidecar como default + perfiles with-ollama, with-browser, with-claude que instalen lo necesario. Hoy todo es manual o comentado.
  9. CI que valide el docker compose up: un job que levante el compose, hit /api/status, y baje. Hoy CI valida tests pero no que el container arranque.
  10. Backup automático del volume aibot_config: ya existe export:system pero es manual. Un cron del host que corra docker exec aibot bun run export:system -- --out /backups/$(date).tar.gz semanalmente.

Features que le agregaría al framework

  1. Webhook mode para Telegram además de long-polling: permitiría >1 réplica detrás de un LB (con stickiness por bot). Hoy el replicas:1 es hard limit por el polling.
  2. RAG over productions: hoy las productions se trackean pero no se indexan en memory.db. Un bot podría回忆ar sus outputs previos relevantes.
  3. Skill marketplace: el find-skills existe en opencode pero no en aibot. Un registry de skills instalables via bun run add-skill <url>.
  4. Streaming de tool calls al dashboard: además de /ws/activity, un panel que muestre tool calls en vuelo con sus argumentos y resultados en tiempo real.
  5. A/B de system prompts: el SystemPromptBuilder es determinista. Poder variantar y medir karma por variante.
  6. Multi-modelo por intención: un router que mande reflection a un modelo grande y topic-guard a uno chico/fast. Hoy failover es lineal, no por task.
  7. Memory compaction en background: hoy la consolidación es parte del health check. Un job separado que corra nightly sin bloquear el agent loop.
  8. Per-bot rate limit de LLM cost: el tenant rate limit es por request HTTP, no por token de LLM. Un bot en loop podría quemar el budget de Ollama Cloud.
