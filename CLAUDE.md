## Comandos
- `bun test` — suite completa. `bun run lint` (Biome), `bun run typecheck` (tsc). CI corre los tres.
- `bun run format` reescribe archivos: no es un check.
- `docker compose up -d --build` — rebuild + restart del contenedor en vivo (reinicia la flota).
- `bun scripts/docker/backup.ts backup` — backup de los volúmenes antes de tocar datos (`restore … --force` pisa los volúmenes vivos).

## Gotchas
- **Verificación de cambios en el frontend (`web/`)**: lo que corre en `127.0.0.1:3000` es el contenedor `aibot-framework-aibot-1`, y el `Dockerfile` hace `COPY web ./web` — los assets están horneados en la imagen. Editar `web/style.css` o `web/pages/*.js` en el host NO cambia nada en el contenedor por sí solo, y el fallo es silencioso: el navegador muestra la UI vieja y ningún log lo menciona. Antes de decir que un cambio de UI está listo, verificar que llegó:
  1. `docker-compose.override.yml` (versionado, se mergea solo) monta `./web` sobre `/app/web` en modo read-only, así que un refresh del navegador alcanza. Si el contenedor se levantó con `-f docker-compose.yml` solamente, el montaje no está.
  2. Cambios en `src/` siguen necesitando `docker compose up -d --build`.
  3. Comprobar el asset servido, no el archivo del repo: `curl -s http://127.0.0.1:3000/style.css | grep <lo-que-cambiaste>`.
- **El estado vivo está en los volúmenes Docker**, no en `data/` ni `config/bots.json` del host (están viejos).
- **`Dockerfile` y `docker-entrypoint.sh` deben quedar con finales de línea LF**; editarlos con herramientas de Windows rompe el contenedor en silencio.
- **Worktrees** (ver working agreements §3): cada worktree nuevo necesita su propio `bun install`. El contenedor sólo ve `D:aibot-framework` (build context y montaje de `web/`), así que un cambio hecho en un worktree no aparece en `127.0.0.1:3000` hasta mergearlo y tenerlo en la carpeta principal.
- **El login del dashboard bloquea la automatización del navegador**: verificar con tests, `curl` o smoke-imports.

## Arquitectura del Bot

El core del bot vive en `src/bot/` como módulos enfocados compuestos por un facade (`BotManager`).
El API pública es `BotManager` — se importa desde `src/bot/index.ts`.

### Backends LLM (`src/core/llm-client.ts`)

`createLLMClient(opts)` decide qué cliente recibe cada bot. **El fallback cross-backend es opt-in**: `CreateLLMClientOptions.crossBackendFallback` + `claudeCli.crossBackendFallback` (ambos default `false`, wireados en `bot-manager.ts`). Antes, sin cadena `failover` configurada, todo bot con `llmBackend: 'claude-cli'` recibía `LLMClientWithFallback(claude, ollama)` y **cualquier** llamada Claude fallida se re-emitía a Ollama en silencio — no sólo el planner: skill de reflexión, soul health check, quality reviewer, memory consolidator y el camino de conversación. Hoy un bot `claude-cli` recibe el `ClaudeCliLLMClient` pelado salvo que se prenda el flag.

Con `failover.enabled`, `orderCandidatesByBackend(candidates, backend)` pone primero el backend propio del bot y `resolveOllamaModels(ollamaClient, opts)` toma los modelos configurados del cliente (antes el primario era `ollamaClient.toString()`, o sea `[object Object]`). `LLMClient.getBackendClient(backend)` es parte de la interfaz y lo implementan los dos clientes concretos y los dos wrappers. `TokenUsage.backend` existe como campo opcional pero **hoy ningún productor lo setea** (`ollamaUsage()` / `parseClaudeUsage()` no lo escriben), así que el query log cae al `?? llmBackend`.

Imágenes con `claude-cli`: `ClaudeCliLLMClient` las manda como bloques de imagen (últimas 8); con imágenes el prompt va por stdin en `--input-format stream-json` y se lee el evento `result` (`buildClaudePromptInput` / `extractStreamJsonResult` en `src/claude-cli.ts`). Antes se reemplazaban por una nota de "sin visión".

**Cancelación** (`src/core/abort.ts`): `signal?: AbortSignal` en las opciones de chat/generate; un abort nunca dispara fallback de modelo ni de backend ni reejecuta tools (`LLMAbortedError`, nombre `AbortError`; un `TimeoutError` por request sí puede caer al fallback). Claude CLI: mata el proceso y espera ≤ 5 s (`ABORT_TOOL_SETTLE_MS`) la callback de tool en curso. Tools largas leen `args._signal` (`exec` mata el árbol, `web_fetch` aborta, MCP `callTool(…, { signal })` manda `notifications/cancelled`, `browser` sólo deja de esperar). **Semáforo** (`src/core/cli-semaphore.ts`): `claudeCli.maxConcurrent` (default 3, se aplica al boot) procesos Claude CLI a la vez para todos los callers, prioridad `interactive` (conversación) > `loop` > `worker`; `getClaudeCliStats()`.

Los errores del Claude CLI llegan como `ClaudeCliError` (`src/claude-cli.ts`) con `exitCode`, `apiErrorStatus`, `isError`, `terminalReason`, `resultText` y `resetsAt`; `parseResetsAt()` convierte el hint `resets 12:20pm (zona)` en un instante absoluto.

### Módulos Relay (`src/relay/`)

Mensajes de una persona a otra a través de un bot, en los dos sentidos (plan: `docs/plans/relay-plan.md`). Un relay es el registro durable de lo que alguien pidió pasar, más la obligación —del sistema, no del modelo— de devolver la respuesta. Operador y usuarios usan el mismo mecanismo; sólo cambia la policy. Config: `bots[].relay { enabled: true, peerToPeer: false, locale: 'es' \| 'en' }` (`enabled: false` = se manda como el bot, sin header ni vuelta).

| Archivo | Responsabilidad |
|---|---|
| `types.ts` | `DeliveryStatus` (`delivered` = llegó a una persona \| `queued` = guardado, nadie avisado \| `failed`), `DeliveryAttempt`, `DeliveryOutcome` (`attempts`, `viaBotId`, `telegramMessageId`), `RelayParty`, `RelayStatus` (+ `answered`), `RelayRecord` (`from: null` = el bot mismo) |
| `config.ts` | `RELAY_DEFAULTS`, `resolveRelayConfig(bot)`. Schema: `BotRelayConfigSchema` en `src/config.ts` |
| `policy.ts` | `canRelay(from, to, { peerToPeer })`: `from` null, cualquiera → operador y operador → cualquiera, permitidos; persona → persona sólo con `peerToPeer`. La razón del rechazo vuelve como output del tool |
| `format.ts` | Puro: `formatReplyPlaceholder` ("Respuesta para Ana", ≤ 64), header estampado por el sistema ("📨 De X (vía Bot):"), footer "respondé a este mensaje" con `expectsReply`, respuesta con cita (`ANSWER_QUOTE_CHARS` = 80), ack / no-entregado deterministas, en `es`/`en`. `relayDedupeKey` (bot, remitente, destinatario, texto normalizado → 16 hex de sha256) |
| `delivery.ts` | `deliverToContact`: orden fijo Telegram (canales verificados primero; cada uno por la instancia propia y después la flota; un 403 / "chat not found" pasa a la siguiente, `isTelegramUnreachable`) → WhatsApp → web. Web es `delivered` sólo con `isWebLive` (hoy no wireado: siempre `queued`, `WEB_QUEUED_NOTE`); una address no numérica se rechaza en vez de escribirse en la sesión compartida `private:0` (`webSessionUserId`). Opciones: `prefer` (un kind primero y después el orden normal; web preferido sólo cuenta si está vivo, si no queda como último recurso) y `telegram` (opciones extra de `sendMessage`). Nunca lanza; nunca dice más de lo que pasó |
| `store.ts` | `RelayStore`: `<paths.data>/relays/<botId>.jsonl` append-only, gana la última línea por id, carga lazy, líneas malformadas se saltean. `openFor` (esperando respuesta: `isRelayOpen`), `sentBy`, `findDuplicate` (uno `failed` no cuenta), `findByTelegramMessage` / `findByTelegramDelivery` (busca en todos los bots: el relay de un bot headless lo lleva la instancia Telegram de otro) |
| `prompt.ts` | `renderSpeakerSection(speaker, { isGroup })` (ver `system-prompt-builder.ts`) y `renderRelaySections(store, botId, speaker)`: "Messages waiting for this person's answer" (con el id para `replyTo`) y "Messages this person asked you to pass on" (últimos 7 días, con estado); máx. 5 por sección; los hechos de entrega salen sólo de acá |
| `service.ts` | `RelayService`, único camino de todo relay: `ensureOperator`, `speaker` (contacto + `isOperator`, también por las direcciones de `config.operator`), `recipientParty`, `contactFor`, `promptSections`, `send` (dedupe 10 min `RELAY_DEDUPE_WINDOW_MS` → record → entrega → marca `answered` el original → append al transcript de la otra persona), `routeTelegramReply` (reply-to sobre un relay abierto → respuesta al que pidió + ack). Un relay con `expectsReply` sale por Telegram con `force_reply` + placeholder, así la respuesta llega como reply-to y la rutea el paso determinista; respuestas y relays sin `expectsReply` no. `preferChannel` (el `channel` de `send_message`). `botName`: nombre de identidad del soul (dep `displayName`), si no el `name` del config. Lee el config en vivo; nunca lanza por datos |
| `wiring.ts` | `createRelayService` (lo llama `BotManager`): instancias Telegram de la flota (`telegramInstancesFor`, propia primero), WhatsApp, append a la sesión web y al transcript privado (`relaySessionKey`, undefined para addresses no numéricas), `displayName` (`BotManager` pasa `SoulLoader.readIdentityName`, el `name:` de IDENTITY.md) |
| `index.ts` | Barrel re-export |

Consumidores: `src/tools/send-message.ts` (reescrito sobre relays: `recipient` (el id viejo de un contacto fusionado resuelve al contacto en que se fusionó) o `replyTo`, `expectsReply`, `channel` (preferencia, no restricción), `register`; el remitente es `_requester`, nunca un argumento; el resultado empieza con `Delivered` / `NOT delivered` / `Delivery FAILED`), `ConversationGate` (paso 0), `ConversationPipeline` (`requester` + `relayContext`), `BotManager.startBot` (seed del operador). Fixes del mismo cambio: `ask_human` en conversación ya no escribe "needs your input" en el chat de un usuario (`mayNotifyAskingChat` en `src/tools/ask-human.ts`: sólo el chat del operador o uno de reporte del agent loop / collaboration, que inyectan `_memoryViewer: null`), y el fallback de pregunta única de `AskHumanStore` sólo resuelve una pregunta cuya notificación llegó a ese chat (`messageId` presente).

### Patrón de composición

Todos los módulos reciben un `BotContext` compartido (estado mutable por referencia).
Las dependencias circulares (delegation/collaborate tools → CollaborationManager) se resuelven con lazy callbacks `() => collaborationManager`.

### Grafo de dependencias

```
BotManager (facade)
  ├── TenantFacade            (tenant/billing/metering)
  ├── UserDirectory            (persistent contact directory, JSONL per bot)
  ├── RelayService            (relays persona↔persona: usa UserDirectory, SessionManager, instancias Telegram de la flota)
  ├── HookEmitter             (lifecycle hooks: message/llm/tool/compaction/agent-loop events)
  ├── McpClientPool           (MCP server connections, shared pool)
  ├── LlmQueryLog             (persistent JSONL traceability log for all LLM calls)
  ├── SecurityAudit           (startup audit with 24h cooldown, non-blocking)
  ├── ToolRegistry            (sin deps de módulo, registra MCP + A2A + SKILL.md tools, wires send_message sobre RelayService)
  ├── SystemPromptBuilder     (lee ToolRegistry.getDefinitions())
  ├── MemoryFlusher           (sin deps de módulo)
  ├── GroupActivation         (sin deps de módulo)
  ├── ContextCompactor        (usa MemoryFlusher, LLMClient, SessionManager)
  ├── ConversationPipeline    (usa SystemPromptBuilder, MemoryFlusher, ToolRegistry, ContextCompactor, Channel, streaming)
  ├── CollaborationManager    (usa SystemPromptBuilder, ToolRegistry)
  ├── TelegramPoller          (polling loop, inyectado en startTelegramBot)
  ├── BotResetService         (reset soul/memory/sessions/stores)
  ├── BotExportService        (export/import bots as .tar.gz archives)
  ├── HandlerRegistrar        (usa ConversationPipeline, GroupActivation, ConversationGate)
  │   └── ConversationGate    (auth, grupo, bot-to-bot gates, reply-to de relays)
  ├── A2AServer               (A2A JSON-RPC server + AgentDirectory)
  ├── DiscordGateway          (Discord WebSocket gateway, per-bot)
  └── AgentLoop               (orquestador)
      ├── AgentScheduler      (scheduling, concurrency, sleep)
      ├── AgentRetryEngine    (retry con backoff, unified error classification via FailoverLLMClient,
      │                        BackendCircuitBreaker fleet-wide por backend)
      ├── AgentPlanner        (LLM planner; resolvePlannerBackend/selectPlannerClient fijan el backend
      │                        del planner+strategist sobre el cliente bare)
      ├── AgentStrategist     (strategist, goals)
      └── AgentLoopUtils      (funciones puras, countFeedbackSignals, evaluateEngagementGate)
```

Fuera del facade, dos paquetes de sólo lectura/mantenimiento montados en `src/web/server.ts`: `src/stats/` (`/api/stats`) lee `BotManager.getAgentLoopState()` / `getChannelState()` y los directorios de datos; `src/hygiene/` (`/api/hygiene`) recibe `toolSucceededRecently` (desde el tool-audit vía `stats/readers/tool-audit`) y `channelStateOf` (desde `BotManager.getChannelState`). Ninguno escribe estado del bot en runtime.
